01 · 상태와 화면

화면은 상태를 비추는 거울

render() · 1353줄 / ui · 924줄 / T · 917줄

데이터는 두 그릇에 나뉘어 있어요. ui는 나만 보는 상태(지금 보는 장소, 카드 회전 각도, 열린 탭)이고, T는 팀 전체가 공유하는 상태(푼 문제, 지운 용의자, 쓴 힌트)예요. render()는 이 둘을 보고 어느 화면을 그릴지 고른 다음, HTML 문자열을 통째로 갈아 끼워요.

function render(){

①과 ③이 왜 필요할까요? innerHTML로 통째로 바꾸면 입력창도 새로 만들어져서, 치던 글자와 커서 위치가 날아가요. 그래서 바꾸기 전에 저장하고 바꾼 뒤 되돌려요. React 같은 도구는 바뀐 부분만 고쳐서 이 문제를 처음부터 피하는데, 그게 바로 React가 존재하는 이유 중 하나예요.

직접 해 보기

  2. ui.view = 'L3'; render()를 실행해 화면이 라운지로 바뀌는지 봐요. 상태만 바꾸고 그렸을 뿐이에요.
02 · 이벤트

클릭 처리기는 딱 하나

document.addEventListener('click') · 1437줄

버튼마다 onclick을 다는 대신, document 하나가 모든 클릭을 받아요. 클릭된 요소에서 위로 올라가며 data-act가 붙은 가장 가까운 조상을 찾고(closest), 그 값으로 할 일을 고르죠. 이걸 이벤트 위임이라고 해요. 화면을 매번 새로 그려도 처리기를 다시 달 필요가 없다는 게 핵심 장점이에요.

두 줄을 비교해 보세요. 'sus'는 commit()으로 팀 상태를 바꾸고, 'g-rot'은 ui만 바꿔요. 카드를 돌리는 건 내 화면에서만 일어나야 하니까요. 좌석 배치도에서 이름을 눌러 지우는 기능도 버튼에 data-act="sus"만 붙여서 만들었어요. 처리기는 하나도 안 고쳤어요.

직접 해 보기

  1. 구멍 카드 옆에 "반시계로 돌리기" 버튼을 추가해 봐요. 버튼에 data-act="g-rot-back"을 붙이고, case 'g-rot-back': ui.gRot = (ui.gRot+3)%4; render(); break;를 넣으면 끝이에요.
  2. 왜 -1이 아니라 +3일까요? (0-1)%4를 Console에 쳐 보면 답이 나와요.
03 · HTML 만들기

문제 하나는 함수 하나

05 · 알고리즘

구멍 카드: 2차원 배열을 90° 돌리기

GR_MSG · 502줄 / GR_H0 · 503줄 / GRID · 504줄

4×4 칸에 구멍이 4개 뚫린 카드를 네 번 돌리면 16칸을 한 번씩 다 지나가요. 코드는 반대로, 문장을 구멍 위치에 차례로 써 넣어서 유리창 글자판을 만들어요.

글자판 만들기504–512
const GRID = (() => {
  const g = Array.from({length:4}, () => Array(4).fill(''));
  let holes = GR_H0, k = 0;
  for (let t = 0; t < 4; t++) {
    // 왼쪽 위부터 읽도록 (행, 열) 순으로 정렬한 뒤 글자를 하나씩 채운다
    [...holes].sort((a,b) => a[0]-b[0] || a[1]-b[1]).forEach(([r,c]) => { g[r][c] = GR_MSG[k++]; });
    holes = holes.map(([r,c]) => [c, 3-r]);   // 시계 방향 90° 회전
  }
  return g;
})();

핵심은 [r, c] → [c, 3-r] 한 줄이에요. 맨 윗줄(r=0)이 맨 오른쪽 열(c=3)이 되니 시계 방향이에요. 화면에서는 같은 회전을 CSS transform: rotate(90deg)로 보여 주니까, 수학과 그림이 맞아떨어져야 퍼즐이 성립해요.

직접 해 보기

  1. 종이에 4×4 칸을 그리고 구멍 (0,3)이 네 번 돌면서 어디로 가는지 따라가 봐요.
  2. GR_H0를 바꾸면 겹치는 칸이 생길 수 있어요. 16칸이 모두 다른지 확인하는 함수를 만들어 봐요. 힌트: new Set(…).size === 16
06 · 알고리즘

밀기 퍼즐: 항상 풀 수 있게 섞기

slideShuffle · 1388줄 / slideSolved · 1387줄 / case 'slide' · 1473줄

3×3 조각을 아무렇게나 섞으면 절반은 절대 풀 수 없는 배치가 나와요. 그래서 이 게임은 섞지 않고, 완성된 상태에서 빈칸을 80번 무작위로 움직여요. 실제로 가능한 이동만 했으니, 거꾸로 되돌리면 반드시 풀려요.

섞기1388–1398
let a = [0,1,2,3,4,5,6,7,8], b = 8, prev = -1;   // 8 = 빈칸, b = 빈칸 위치
for (let k = 0; k < 80; k++){
  const r = Math.floor(b/3), c = b%3, nb = [];
  if (r>0) nb.push(b-3); if (r<2) nb.push(b+3);   // 위·아래 이웃
  if (c>0) nb.push(b-1); if (c<2) nb.push(b+1);   // 왼쪽·오른쪽 이웃
  const opts = nb.filter(x => x !== prev), n = opts[Math.floor(Math.random()*opts.length)];
  [a[b], a[n]] = [a[n], a[b]]; prev = b; b = n;              // 구조 분해로 맞바꾸기
}

1차원 배열 칸 번호 i를 Math.floor(i/3)(행)과 i%3(열)로 바꾸는 계산이 계속 나와요. 2차원 판을 1차원 배열로 다루는 아주 흔한 기술이에요. prev는 방금 온 칸으로 바로 되돌아가는 헛걸음을 막아요.

직접 해 보기

  1. 클릭 처리기의 case 'slide'에서 "옆 칸인지" 판단하는 adj 조건을 읽어 봐요. 왜 Math.abs(i-b) === 1만으로는 부족할까요? (2번 칸과 3번 칸을 생각해 보세요.)
  2. 80을 4로 바꾸면 퍼즐이 얼마나 쉬워지는지 해 봐요.

팀원 화면에 바로 뜨는 원리

commit · 1000줄 / fireBackend · 958줄 / goOffline · 1009줄

팀 상태를 바꿀 때는 항상 commit()을 불러요. 내 화면의 T를 먼저 바꾸고(그래서 즉시 반응해 보이고), 그다음 서버(Firebase)에 바뀐 부분만 보내요.

  2. deepMerge(545줄)는 재귀 함수예요. deepMerge({a:{x:1}}, {a:{y:2}})의 결과를 먼저 예상하고 실행해 봐요.

버그 해부: 유리창이 사라진 이유

.grille-box · 213줄 / .glass · 214줄

현장 감식관의 창가 문제에서 글자가 버튼 위로 쏟아져 나온 버그, 기억나요? 원인은 CSS 한 줄이었어요.

/* 부모: 첫 칸은 내용물 크기만큼(auto) */
.grille-box{ grid-template-columns: auto minmax(0,1fr) }
/* 고치기 전: 내 너비 = 칸 너비의 100%  →  칸 너비 = 내 너비 … 서로 기다림 */
.glass{ width: min(300px, 100%) }
/* 고친 뒤: 300px로 정해 두고, 좁은 화면에서만 줄어들게 */
.glass{ width: 300px; max-width: 100% }

auto 칸은 안에 든 것의 크기를 보고 너비를 정하는데, 안에 든 유리창은 "칸 너비의 100%"로 정하겠다고 하니 서로 상대를 기다리는 꼴이 됐어요. 브라우저는 이 순환을 0으로 풀어 버렸고, 글자를 담은 판만 너비가 0인 상자 밖으로 흘러넘쳤어요. 퍼센트 크기는 부모 크기가 먼저 정해져 있어야 의미가 있다는 걸 기억하면 이런 버그를 피할 수 있어요.

  • 이 파일의 다크 모드도 볼 만해요. 색을 전부 --ink, --surface 같은 CSS 변수로 정의하고(13줄), prefers-color-scheme: dark일 때 변수 값만 바꿔요(26줄).
  • 반응형은 @media (max-width:760px)(329줄)에서 2단 배치를 1단으로 바꾸는 식이에요.

직접 해 보기

  1. 개발자 도구 Elements 탭에서 .glass의 width를 min(300px,100%)로 되돌려 보고, 버그가 다시 나타나는지 직접 봐요.
  2. Rendering 패널에서 "prefers-color-scheme: dark"를 켜서 다크 모드를 확인해 봐요.

부스 예약 DB 문제 풀이

게임 속 SQL 문제를 그대로 옮겼어요. 먼저 직접 풀어 보고, 아래 풀이를 열어 보세요.

idboothstart_timeend_timeheadcountstatus
1A13:0014:001'OK'

SELECT SUM(headcount)
FROM reservation
WHERE start_time >= '13:00'
  AND end_time <= '14:00'
  AND status <> 'CANCEL';
풀이 보기 (정답 포함)

WHERE 조건 세 개를 모두 통과한 행의 headcount만 더해요. 행마다 따져 보면 이래요.

id시작 ≥ 13:00끝 ≤ 14:00status ≠ CANCEL결과
1참참참포함 +1
2참참참포함 +3
3참참UNKNOWN제외
4참참거짓제외
5참거짓 (15:00)참제외
6거짓 (12:00)참참제외

정답은 1 + 3 = 4예요. 함정은 3번 행이에요. SQL에서 NULL은 "값을 모름"이라서, NULL <> 'CANCEL'은 참도 거짓도 아닌 UNKNOWN이 돼요. WHERE는 참인 행만 통과시키니 3번 행은 빠져요. NULL을 "CANCEL이 아님"으로 읽으면 5라고 답하게 되는 함정이에요.

NULL인 행도 넣고 싶다면 이렇게 써야 해요:

AND (status <> 'CANCEL' OR status IS NULL)
-- 또는
AND COALESCE(status, '') <> 'CANCEL'

하나 더: 시각을 '13:00' 같은 문자열로 비교해도 맞게 나오는 건 두 자리 숫자가 같은 형식으로 맞춰져 있어서예요. '9:00'처럼 자릿수가 다르면 '9:00' > '13:00'이 되어 버려요. 실무에서는 TIME이나 DATETIME 타입을 써요.

직접 해 보기

  1. COUNT(*)와 COUNT(status)는 이 표에서 각각 몇일까요? (NULL을 세는지 안 세는지가 달라요.)
  2. 6번 행(12:00~13:00)도 13시 정각까지 쓴 예약이에요. "13시~14시 사이에 조금이라도 겹친 예약"을 구하려면 조건을 어떻게 바꿔야 할까요?
